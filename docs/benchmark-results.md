# Benchmark results

Every number here was produced by `vectordb-bench` on the machine described
below. Nothing is estimated, extrapolated, or carried over from another
configuration. Where a figure is missing, it is missing because it was not
measured — see [Not measured](#not-measured).

Reproduce with:

```sh
cmake --preset release && cmake --build --preset release
./build/release/bin/vectordb-bench
```

Methodology: [benchmarking.md](benchmarking.md).

## 1. Distance kernels

One `l2_squared` call on two cache-resident vectors. This measures **arithmetic
throughput**, not the memory-bound scan — both operands stay in L1, which is why
the GB/s figures far exceed DRAM bandwidth.

| kernel | dim | ns/call | GB/s | speedup |
|---|---|---|---|---|
| scalar | 128 | 37.1 | 27.6 | 1.00× |
| **neon** | **128** | **10.3** | **99.1** | **3.59×** |
| scalar | 384 | 100.4 | 30.6 | 1.00× |
| **neon** | **384** | **24.3** | **126.2** | **4.13×** |
| scalar | 768 | 200.0 | 30.7 | 1.00× |
| **neon** | **768** | **51.0** | **120.6** | **3.92×** |
| scalar | 1536 | 398.7 | 30.8 | 1.00× |
| **neon** | **1536** | **106.7** | **115.2** | **3.74×** |

**3.6–4.1×**, which is what a 4-lane SIMD unit should give. The scalar kernel is
already unrolled with four independent accumulators, so this is genuinely the
lane-width win rather than a comparison against a naive loop.

The 128-dimension case is slightly below the rest because the fixed per-call
overhead — the indirect call, the loop setup, the horizontal reduction — is a
larger fraction of a shorter loop.

## 2. Brute-force search latency

`k = 10`, L2, one query at a time, 100 queries per configuration.

| dim | N | p50 (µs) | p95 (µs) | effective GB/s |
|---|---|---|---|---|
| 128 | 10,000 | 133.2 | 136.0 | 38.5 |
| 128 | 100,000 | 1,288.7 | 1,372.0 | 39.7 |
| 768 | 10,000 | 642.7 | 669.2 | 47.8 |
| 768 | 100,000 | 6,413.1 | 7,648.4 | 47.9 |

Two things to read here.

**Latency is linear in N**, exactly as `O(N·D)` predicts: 10× the vectors, 10×
the time, to within noise.

**Throughput plateaus at 38–48 GB/s regardless of dimension**, which is the
machine's memory bandwidth. The scan is **bandwidth-bound, not compute-bound** —
and that is why NEON's 3.9× on the kernel does not become 3.9× here. Making the
arithmetic faster does not help a loop that is waiting for bytes.

It also explains why HNSW's advantage is real: it does not compute faster, it
**touches less data**.

## 3. HNSW: build, latency and recall

`M = 16`, `efConstruction = 200`, L2, `k = 10`, 200 queries.

### N = 50,000, D = 128

Build: **7.73 s** (6,466 vectors/s). Index: **6 MB**, 145 bytes/vector, 5 layers.

| efSearch | p50 (µs) | p95 (µs) | recall@10 | vs brute force |
|---|---|---|---|---|
| 10 | 20.0 | 30.1 | 0.9590 | **32.3×** |
| 20 | 25.0 | 36.0 | 0.9880 | 25.9× |
| 50 | 35.4 | 46.5 | 0.9950 | 18.3× |
| 100 | 46.6 | 59.0 | 1.0000 | 13.9× |
| 200 | 66.6 | 84.5 | 1.0000 | 9.7× |
| 400 | 149.1 | 186.2 | 1.0000 | 4.3× |

### N = 20,000, D = 768

Build: **9.59 s** (2,086 vectors/s). Index: **2 MB**, 145 bytes/vector, 4 layers.

| efSearch | p50 (µs) | p95 (µs) | recall@10 | vs brute force |
|---|---|---|---|---|
| 10 | 53.8 | 69.0 | 0.9760 | **24.0×** |
| 20 | 59.4 | 70.2 | 0.9980 | 21.7× |
| 50 | 71.0 | 89.4 | 1.0000 | 18.1× |
| 100 | 84.4 | 104.0 | 1.0000 | 15.3× |
| 200 | 180.4 | 245.0 | 1.0000 | 7.1× |
| 400 | 351.0 | 425.1 | 1.0000 | 3.7× |

### Reading these

**The knee is at efSearch ≈ 20.** Recall goes 0.959 → 0.988 for a 25% latency
increase; going further buys 0.012 recall for another 40%, and beyond 100 buys
nothing at all on this data. If you take one number from this document, it is
that the default `efSearch = 64` is conservative for datasets of this size.

**Index overhead is 145 bytes/vector at M = 16**, independent of dimension —
which follows directly from the formula, since edges do not scale with D. At
D = 128 that is 28% on top of the 512-byte payload; at D = 768 it is 4.7%. HNSW
is proportionally much cheaper for the high-dimensional vectors people actually
store.

**Recall reaches 1.000 and stays there.** At these sizes HNSW is effectively
exact, and recall stops being a useful signal. The interesting recall/latency
trade only appears at larger N — see [Not measured](#not-measured).

**Build is `O(N log N)` searches**, and it shows: 6,466 vectors/s at D = 128
versus 2,086 at D = 768, roughly tracking the 6× dimension increase.

## 4. Concurrent batch search

N = 50,000, D = 128, 2,000 queries, `k = 10`, `include_metadata = false`.

| threads | queries/s | scaling |
|---|---|---|
| 1 | 51,368 | 1.00× |
| 2 | 98,875 | 1.92× |
| 4 | 187,410 | 3.65× |
| 8 | 214,987 | **4.19×** |

Near-linear to 4 threads, then it flattens. Two reasons, and they compound: the
M1 has 4 performance and 4 efficiency cores, so threads 5–8 are on slower cores;
and the workload is memory-bound, so extra threads contend for the same
bandwidth.

### The bug this benchmark found

The first run of this benchmark reported **13 million queries/second**, which is
physically impossible — it was searching an empty database, because the setup
never flushed before reopening. The driver now asserts that the database holds
the expected number of vectors and that a probe query returns `k` results,
before timing anything.

The second run reported honest numbers with a *negative* scaling curve: 1.79× at
2 threads, then 1.16× at 4 and 0.90× at 8.

Profiling eight concurrent searchers found **89% of search time inside
`MetadataStore::get`**, nearly all of it blocked on that class's mutex, with
SQLite's WAL `fcntl` locking underneath. `Database::search` was fetching
metadata for every result even when the database had none and the caller had not
asked for it.

Skipping the lookup when it cannot contribute took single-thread throughput from
28,357 to 51,368 queries/s and restored scaling from 0.90× to 4.19×.

Two lessons worth keeping: a benchmark needs correctness assertions or it will
happily report a wonderful number for a broken configuration; and the bottleneck
was two layers away from the code being optimised.

## 5. Persistence

N = 50,000, D = 128, HNSW.

| | |
|---|---|
| Insert + index build | 7.78 s (6,428 vectors/s) |
| Flush to disk | 0.113 s |
| Reopen + load + validate | **0.009 s** |
| `vectors.bin` | 25 MB |
| `index.hnsw` | 6 MB |

**Loading is ~860× faster than rebuilding** (9 ms versus 7.8 s), which is the
entire justification for persisting the index rather than rebuilding on every
open. Those 9 ms include validating every neighbour reference in the graph.

`vectors.bin` at 25 MB is 50,000 × 128 × 4 = 25.6 MB of payload plus 13
bytes/slot of ids, norms and liveness — 0.6% overhead.

## Why the data matters

An earlier version of the dataset generator drew query vectors from a
*different* cluster structure than the data. Every query landed in the empty
space between clusters, where a query's 10th nearest neighbour sat 3% further
away than its 1st, against 15% for a genuine in-distribution point.

HNSW measured **recall@10 = 0.752** at parameters that should be near-exact. The
graph was correct; the benchmark was measuring tie-breaking among hundreds of
near-equidistant points.

With queries drawn from the same structure, the same configuration measures
0.959 at `efSearch = 10`.

**If an ANN benchmark shows terrible recall, suspect the data before the index.**
The fix is in `generate_queries`, and the reasoning is in
[`learnings/40-search-indexes/02-approximate-nearest-neighbour.md`](../learnings/40-search-indexes/02-approximate-nearest-neighbour.md).

## Not measured

Stated explicitly, because an absent number is more honest than an estimated
one.

- **AVX2.** Implemented, compiled, guarded by runtime detection and validated
  against the scalar kernel by the same test suite every kernel runs — but never
  executed on x86-64 hardware by this project. No AVX2 figures appear above.
- **N = 1,000,000.** At D = 768 that is 3 GB of vectors on an 8 GB machine, and
  the numbers would measure swap. D = 128 would fit (512 MB) and is the obvious
  next run.
- **Insertion throughput under concurrency.** Concurrent writes are not
  supported, so there is nothing to measure.
- **Filtered search latency.** The post-filter's cost depends entirely on filter
  selectivity, and a single number would mislead.
- **`mmap` versus buffered reads.** The load path maps the file; the alternative
  was never implemented, so there is no comparison to report.
- **Comparison against FAISS or hnswlib.** The most useful number in this
  document would be "how far are we from a mature implementation?", and it is
  absent. Adding an external backend purely as a benchmark baseline is in
  [`learnings/next-steps.md`](../learnings/next-steps.md).
