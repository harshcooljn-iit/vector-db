# AVX2, and the runtime-detection problem

🔴 Advanced · pairs with `src/distance/kernel_avx2.cpp` and `cpu_features.cpp`

> **Honesty first.** This kernel is compiled, reviewed, guarded by runtime
> detection and validated against the scalar kernel by the same test suite every
> kernel runs. It has **never been executed on x86-64 hardware** by this
> project — development happened on Apple Silicon. `docs/benchmark-results.md`
> reports no AVX2 numbers rather than estimated ones. Read this note for the
> *mechanism*, not for a performance claim.

## Why x86 is harder than ARM

NEON is mandatory on arm64: if you are running, you have it.

x86-64 is a 20-year-old ISA with a long tail of optional extensions:

| Extension | Year | Width |
|---|---|---|
| SSE2 | 2001 | 128-bit (baseline for x86-64) |
| AVX | 2011 | 256-bit |
| AVX2 | 2013 | 256-bit integer + FMA |
| AVX-512 | 2016 | 512-bit, fragmented support |

A binary must run on a machine older than the one that compiled it. So the
kernel must be **selected at runtime**.

## What happens if you skip the check

```cpp
// Compiled with -mavx2, called unconditionally:
__m256 sum = _mm256_setzero_ps();
```

On a CPU without AVX2 this is **SIGILL — illegal instruction**. The process
dies. No exception, no diagnostic, nothing to catch.

And it works perfectly on the developer's machine. This is the bug that ships.

## The check, in four parts

```cpp
bool detect_avx2() noexcept {
    if (cpuid(0, 0).eax < 7) return false;          // 1. too old to ask

    const CpuidResult leaf1 = cpuid(1, 0);
    if (!(leaf1.ecx & (1 << 27))) return false;     // 2. OSXSAVE
    if (!(leaf1.ecx & (1 << 28))) return false;     //    AVX
    if (!(leaf1.ecx & (1 << 12))) return false;     //    FMA

    if ((read_xcr0() & 0x6) != 0x6) return false;   // 3. the OS saves YMM

    return (cpuid(7, 0).ebx & (1 << 5)) != 0;       // 4. AVX2 itself
}
```

**Part 1** — old CPUs do not support the leaf that reports extended features.
Asking anyway returns garbage.

**Part 2** — AVX2 needs FMA in our kernel, and AVX2-without-FMA is possible in
principle. Check what you use.

**Part 3 is the one people skip, and it is a real crash.** A CPU can support AVX2
while the *operating system* does not save the 256-bit YMM registers across a
context switch. Using AVX2 there corrupts state or faults. `XCR0` is the
extended control register; bits 1 and 2 say the OS is preserving SSE and AVX
state. **CPUID alone is not enough.**

**Part 4** — AVX2 lives in a different leaf from AVX.

Detection runs **once**, cached in a function-local static. `cpuid` is a
serialising instruction — it drains the pipeline — so calling it per query would
be a self-inflicted stall.

## The compilation problem

You cannot compile the whole file for AVX2:

```cmake
target_compile_options(vectordb PRIVATE -mavx2)   # DON'T
```

That would compile the *runtime check itself* with AVX2, and it would crash
before it could decide anything. The check must run on the oldest CPU you
support.

The fix is a function-level attribute:

```cpp
#define VECTORDB_AVX2 __attribute__((target("avx2,fma")))

VECTORDB_AVX2 float avx2_l2_squared(const float* a, const float* b, std::size_t n);
```

Only that function is compiled with AVX2. Everything else in the file, including
the dispatch, stays at baseline. Supported by GCC and Clang; MSVC uses a
different mechanism (`/arch:` per file, or separate translation units).

## The kernel

Same shape as NEON, wider:

```cpp
constexpr std::size_t kBlock = 32;    // 4 accumulators × 8 lanes

__m256 sum0 = _mm256_setzero_ps();
for (; i + 32 <= count; i += 32) {
    const __m256 d0 = _mm256_sub_ps(_mm256_loadu_ps(a+i), _mm256_loadu_ps(b+i));
    sum0 = _mm256_fmadd_ps(d0, d0, sum0);
    // ... d1, d2, d3
}
```

### `loadu`, not `load`

```cpp
_mm256_loadu_ps(ptr);   // unaligned — always correct
_mm256_load_ps(ptr);    // requires 32-byte alignment, FAULTS otherwise
```

Since stride equals dimension, rows are only 4-byte aligned for odd dimensions.
The aligned form would be a segfault. On every AVX2-capable microarchitecture,
an unaligned load that does not straddle a cache line costs the same anyway.

### The horizontal sum is uglier than NEON's

NEON has `vaddvq_f32` — one instruction. x86 does not, so you fold:

```cpp
__m128 low  = _mm256_castps256_ps128(value);   // lower 128 bits
__m128 high = _mm256_extractf128_ps(value, 1); // upper 128 bits
__m128 sum = _mm_add_ps(low, high);            // 8 → 4
sum = _mm_add_ps(sum, _mm_movehl_ps(sum, sum)); // 4 → 2
sum = _mm_add_ss(sum, _mm_shuffle_ps(sum, sum, 0x55)); // 2 → 1
return _mm_cvtss_f32(sum);
```

A tree — three steps, not seven. Once per call, never in the loop.

## The AVX-512 trap, worth knowing

AVX-512 is 512-bit and looks like a free doubling. On many Intel server parts it
is not: heavy AVX-512 use makes the core **downclock**, sometimes by hundreds of
MHz, and it affects *other* threads on the same core.

A workload that is 1.5× faster in the vectorised loop can be slower overall
because everything else slowed down. This is why several performance-focused
projects deliberately stop at AVX2.

The general lesson: **a microbenchmark showing a speedup does not prove a
system-level win.** Measure the system.

## Testing what you cannot run

Two things make an untested kernel acceptable to ship:

1. **It is unreachable where it would break.** Runtime detection means it is
   never selected on a CPU that cannot run it, so the worst case is that it is
   never used.
2. **It is validated by the same suite as every other kernel.** The test file is
   parameterised over `available_kernels()`: every tail length from 1 to 17, a
   double-precision reference on random data, and equality with scalar. On an
   AVX2 machine, that suite runs against AVX2 automatically.

What that does *not* give is a performance number, so none is reported. "It
compiles and is guarded" is not "it is fast", and the difference matters.

If you have an x86-64 machine: build, run `vectordb version` (it prints the
selected kernel), run `ctest`, and run `vectordb-bench distance`. That would fill
the gap in `benchmark-results.md`, and it is a genuinely useful contribution.

## Experiments

1. On an x86 machine, run `vectordb version` and confirm the kernel is `avx2`.
   Then run the kernel tests and the distance benchmark.
2. Remove the XCR0 check and reason carefully about what would break, and on
   what kind of system.
3. Compile the whole file with `-mavx2` instead of using the target attribute,
   and run it on a machine without AVX2 (or in an emulator that lacks it). Watch
   where it crashes — before or after the detection?
4. Add an AVX-512 kernel behind detection and compare against AVX2 on real
   hardware, watching the clock frequency while it runs.
5. Compare the horizontal-sum sequences for NEON and AVX2. Count instructions.
   Consider what that costs at small `D`.
